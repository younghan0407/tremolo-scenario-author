# Grounding 정책 — 예측 금지, 실측 필수 (가드레일)

## 왜
샘플 스크립트/패턴을 보고 **'예측'으로** 셀렉터를 옮겨 적으면 틀리기 쉽다. 같은 메뉴의 '생성'이라도
**진입 포인트·상태에 따라 입력 필드·스텝·셀렉터가 달라진다**(예: 목록에서 생성 vs 상세에서 생성). 그래서
예측 스텝은 반드시 **흔적을 남기고(태그) 라이브 실측으로 확인**해야 한다.

## 태그 규약 (스텝 `note`)
target(셀렉터)을 가진 모든 스텝의 `note` 앞에 상태 스탬프를 붙인다:
- **`[실측]`** = **실측됨**(Grounded). 실제 라이브 DOM에서 존재를 확인함. 예: `"[실측] 2026-08-04 rule-create 화면 확인"`.
- **`[예측]`** = **예측/미확인**(Predicted). 샘플·패턴에서 추정했고 아직 라이브 확인 안 됨. 예:
  `"[예측] instance_create 참고 — 진입점 다르면 상이 가능, 실측 필요"`.
- **미태그**(스탬프 없음) = **예측으로 간주**(안전 기본값). 즉 `[실측]`가 명시적으로 찍혀야만 실측으로 인정.

예외(태그 불필요): `goto`(고정 URL)와 로그인 프리앰블 필드(아이디/비밀번호/인증 코드 — 이미 고정·검증됨).
ground 는 **맨 앞 로그인 묶음(goto + 아이디/비밀번호/인증 코드 입력)만** 프리앰블로 보고 건너뛴다. 본문에 같은 placeholder 의 입력
(예: 장비 IPMI '비밀번호를 입력해 주세요.')이 있어도 일반 스텝으로 실행·판정한다(2026-10-07 개정). 본문의 password 입력은 textbox role 이
없으므로 css(placeholder)로 작성한다. 역할 계정으로 로그인하는 시나리오(자체 로그인 스텝)는 ground 가 공용 계정으로 로그인하므로 실측 대상이 아니다.

## 강제 (verify)
`node scripts/verify.mjs "<spec.ts>"` 는 항상 grounding 요약을 출력한다:
```
ℹ️ grounding (실측 상태) — N 실측 / M 예측(미실측) — 라이브 그라운딩 필요: s10(...), s11(...)
```
- 기본은 정보(soft) — 예측 스텝을 **항상 노출**(흔적).
- **`--require-grounded`** 를 주면 예측 스텝이 하나라도 있으면 **FAIL(하드 차단)**. 신규 스크립트 완료 게이트로 사용.

## 신규 스크립트 필수 절차 (무조건 실측 — 예측에서 멈추지 않는다)
> **사용자가 따로 멈추라고 하지 않았다면, 예측 작성 → 실측 → 수정 → 재실측을 같은 작업 흐름에서 끝까지 연속 진행**해
> **즉시 실행 가능한 스크립트**를 내놓는다. "예측본을 만들었으니 실측은 다음에/사용자 확인 후" 로 끊지 말 것.
> (실측은 비변경이거나 `qa-trml-{yymmdd}` 자원만 바꾸므로 별도 동의가 필요 없다. 동의가 필요한 것은 '1회 실행'(smoke)뿐.)

0. **사전 조사(권장, 가장 큰 단축)**: 작성 전에 `live/walk.mjs` 로 대상 화면을 1~2회 비변경 덤프(필드 라벨 h1·input id/placeholder·
   select·표 헤더·버튼·모달 텍스트)해 셀렉터를 거의 확정한다. 이렇게 하면 '예측' 스텝 자체가 거의 생기지 않는다.
1. 저작: 그래도 추정한 셀렉터는 `note`에 **`[예측]`** 로 표기(흔적 남기기).
2. 생성 + 정적 검증: `generate.mjs` → `verify.mjs` — 구조 PASS + grounding 요약 확인. (재생성해도 기존 실측 스탬프는 보존된다 —
   단 대상·입력값·검증 조건·선택 설정이 바뀐 스텝은 실측이 **무효화**되어 `[예측]` 으로 돌아가고 다시 실측해야 한다.
   표 선택(`antdTableSelect`)·`antdSelect` 처럼 헬퍼 설정으로 대상을 찾는 스텝도 실측 대상에 포함된다.)
3. **라이브 실측(필수, 바로 이어서)**: `node scripts/live/ground.mjs "<spec.ts>" --write --continue --skip-missing --mutate`
   - 실제 화면에서 스텝을 재생하며 각 target 존재·상태를 점검한다. `--mutate` 는 작업 대상이 `qa-trml-{yymmdd}` 자원으로 확인되는
     제출만 **실제로 수행**(생성→검증→수정→삭제까지 끝까지 확인), 그 외 제출은 수행하지 않고 `--continue` 로 그 뒤를 점검한다.
   - 시나리오가 만드는 자원 이름은 `qa-trml-{YYMMDD_HHMMSS}-<용도>` + `runtime.saveAs` 별칭이라 `--mutate` 로 그대로 끝까지 돈다.
     기존 자원이 필요한 구간(사전데이터)은 먼저 `qa-trml-{yymmdd}` 자원을 만들어 두거나(아래 3), 이미 있는 `qa-trml-*` 자원으로
     `--subst 시나리오자원=qa-trml-…` 해 점검한다(아래 '실측 자원 제한').
   - 결과로 note를 **`[실측]`(FOUND) / `[예측]`(MISSING·AMBIGUOUS·UNREACHED·POSTMUT·대체자원 차이)** 로 자동 스탬프.
4. **수정 루프**: MISSING/AMBIGUOUS 는 셀렉터·진입점 문제 → walk 로 원인 확인 → 수정 → **해당 범위만** 재실측(`--range sA:sB`).
5. **완료 판정(done)** — 아래가 모두 충족되면 완료(사용자 대기 없이):
   - 셀렉터 문제(MISSING·AMBIGUOUS 중 사전데이터와 무관한 것) **0건**.
   - 남은 `[예측]` 은 **(a) 사전데이터 부재 (b) 변경 후 결과(POSTMUT) (c) 대체 자원 값 차이** 뿐이고, 보고서에 그 목록과
     필요한 사전데이터를 명시. 사전데이터가 준비되면 `verify --require-grounded` 까지 다시 돌린다.
   - TC 불일치는 아래 원칙대로 표기·보고(수정해서 통과시키지 않음).

## 실측 자원 제한 · CUD 허용 범위 (필수, 2026-10-06 개정)
대상은 여러 팀이 함께 쓰는 **테스트 환경**이다. 즉시 실행 가능한 스크립트를 만들기 위해 자원 변경(CUD)을 허용하되, **대상 자원을 이름으로 제한**한다.
(구 규칙 — `pqa-`/`qa-` 접두 자원·생성자 `pqa-`/`tremolo` 계정 자원 허용, `--owner-ok` — 은 **폐기**. 사람이 수동으로 만든 자원도 `qa-`
 등을 쓸 수 있어 구분이 안 되므로, 하네스·QA 팀이 자동화용으로 만든 것만 쓰는 전용 형식으로 좁혔다.)
1. **허용 자원 = 이름에 `qa-trml-{yymmdd}` 가 들어간 자원만** (예: `qa-trml-261006-vol`, `qa-trml-261006_153000-lb`).
   - **생성·수정·삭제, `--subst` 대체, 생성·수정 폼에서 고르는 기존 자원**은 이 자원만 대상으로 한다.
   - 예외(2026-10-06): **자원을 바꾸지 않는 조회 화면**(구성도·집계 보고서·이벤트 이력 등)에서 필터·트리·드롭다운으로 기존 프로젝트·
     인스턴스·세그먼트를 고르는 것은 허용한다(네트워크 단 차단이 변경을 막는다). 그 화면에 저장·적용 같은 제출이 있으면 그 제출은 규칙대로 막힌다.
   - 예외(2026-10-07): **qa-trml 이름으로 만들 수 없는 기존 인프라**(외부 세그먼트, 이동 대상 컴퓨트 호스트 등)는 **선택만** 허용한다
     — 생성·수정·삭제는 하지 않는다. 이름은 하드코딩하지 않고 실행 세트 맨 앞의 `[준비]-[실행 변수]-[인프라]` 가 별칭
     (`EXT_SEGMENT`·`MIG_HOST` 등, `PRE_` 접두 없음)으로 넘긴다. OS 이미지는 인프라로 보지 않고 `[준비]` 가 qa-trml 이름으로 업로드한다
     (부팅 이미지 파일은 사용자가 `data/testfiles` 에 둔다).
   - 그 외 자원(타 팀 자원, `pqa-*`·`qa-*`·`auto-*`·`__DEFAULT__` 등 공용·시스템 자원 포함)은 쓰지 않는다.
     `ground.mjs` 는 허용되지 않은 `--subst` 대상이 있으면 **실행 전에 중단**하고, `--mutate` 제출은 누르는 순간 화면에서
     대상(열린 행 메뉴의 행 / 선택된 행 전부 / 팝업 내용 / 폼 입력값·제목)이 `qa-trml-{yymmdd}` 로 확인될 때만 수행한다.
   - 허용 자원이 없으면 대체하지 않는다 → 먼저 만들고(아래 3), 만들 수 없으면 `[예측] 미발견`(사전데이터 필요)으로 남기고 보고한다.
2. **스크립트가 만드는 자원 이름**: `qa-trml-{YYMMDD_HHMMSS}-<용도>` 로 쓰고 그 입력 스텝에 `runtime.saveAs: "<별칭>"` 을 단다.
   이후 검색·행 선택·삭제 등은 `{{별칭}}` 으로 참조한다(Tremolo 가 **실행일 기준**으로 이름을 만들고 같은 실행 안에서 재사용).
   - 별칭은 **실행 세트 전체에서 공유**되므로 시나리오마다 겹치지 않게 짓는다(예: `vg14_vol`). 같은 별칭에 다른 값을 넣으면 Tremolo 가 실패 처리.
   - 생성 시나리오는 끝에 **삭제(teardown)** 를 넣어 스스로 정리한다. `ground --mutate` 가 끝에 "생성했을 수 있는 qa-trml 자원" 을 출력하면 남았는지 확인·정리.
   - `verify.mjs` 가 구 규칙 이름(`qa-auto-`/`pqa-auto-`)·날짜 없는 `qa-trml-` 을 경고한다.
3. **사전데이터(기존 자원이 필요한 구간)는 AI 가 직접 만든다**: 이름 `qa-trml-{yymmdd}-<용도>`(예: `qa-trml-261006-lb`). 생성 스텝만 담은
   준비용 시나리오를 만들어 `ground --mutate` 로 실행하면 같은 안전 판정을 거친다. 만든 자원은 보고서 사전 준비 목록에 이름과 함께 남긴다.
4. **타 자원에 영향을 줄 수 있는 동작**(삭제·상태 변경·연결/해제·복원·마이그레이션·일괄 처리·프로젝트/컨텍스트 단위 동작 등)은
   **영향 범위 안의 자원을 모두 `qa-trml-*` 로 구성한 뒤** 수행한다.
   예: VG 삭제(포함 볼륨 함께 삭제) → `qa-trml-*` VG 안에 `qa-trml-*` 볼륨만 / 백업 복원 → `qa-trml-*` 볼륨의 `qa-trml-*` 백업 /
   인스턴스 연결 해제 → `qa-trml-*` 인스턴스·볼륨. 프로젝트 전체·공용 설정을 바꾸는 동작은 이름으로 범위를 한정할 수 없으므로 수행하지 않고 보고한다.
   - 이 구성은 **스크립트에 넣지 않는다.** 스크립트 실행 전 **사전 준비 항목**으로 보고서·`시나리오_설계.md` 사전데이터에 명시한다.
5. 실측 결과에서 **`qa-trml` 이 아닌 대상의 제출이 '수행'으로 찍히면 즉시 중단·점검**한다(정상이면 항상 '미수행').
   새 클릭 헬퍼(xpath/css 버튼)를 만들면 첫 실측 전에 `--mutate` 없이 돌려 그 스텝이 제출로 인식되는지('미수행') 확인한다.
6. **변경 차단은 두 겹**(`scripts/live/mutation.mjs`, ground·walk·smoke 공통):
   - 화면 단: 클릭(role/text/css/xpath·제목 라벨)·입력란 Enter(검색란 제외)·즉시 실행형 행 메뉴(…해제/시작/중지/재시작 등)·walk `clickText`
     를 같은 규칙으로 판정해 변경 동작은 누르지 않는다.
   - 네트워크 단: 로그인 이후 **GET 이 아닌 요청은 모두 차단**된다. 화면 단이 놓친 동작(이름 없는 아이콘 버튼, 팝업 없는 즉시 실행 등)이
     요청을 보내면 막히고 그 스텝은 `변경 요청 차단(… POST /api/…)` 으로 보고된다(이후 결과 확인은 '변경 후 결과').
     열리는 경우는 셋뿐: `--mutate` 에서 **누르는 요소 기준** 대상(그 행 / 메뉴를 연 행 / 그 팝업 / 선택 행 / 폼)이 `qa-trml-{yymmdd}` 로
     확인된 스텝, walk 액션에 `"writeOk": true` 를 명시한 경우(예: 프로젝트 컨텍스트 전환 [확인]), 세션 연장 [연장].
     '선택 행'은 **표의 선택 열(`ant-table-selection-column`)로 고른 행**만이다 — 팝업 안 입력 표의 일반 체크박스(예: 서버 등록 CPU 행의
     'Hyper Thread 활성화')는 입력값이지 선택이 아니다(2026-10-07 개정).
   - 조회·로그인 유지에 GET 이 아닌 요청이 필요한 환경이면(조회가 계속 '변경 요청 차단'으로 막힘) 그 요청만 `envs.json` 의
     `envs.<키>.live.allowRequests` 에 정규식(`"^POST /api/v1/search"` 형태)으로 추가한다 — 서버 상태를 바꾸지 않는 요청인지 확인한 뒤에만.
     전역 `live.allowRequests` 에는 현재 두 종류만 있다: 세션 유지(`/v1/bootfactory/api/token/(extend|verify/refresh|expired/refresh)`)와
     CONTRABASS 집계 화면의 조회·차트·CSV(`POST /v1/contrabass/admin/aggregation/<화면>/(search|export|chart)`, 2026-10-07 walk 로 조회 전용 확인).
     **계정·화면 설정을 저장하는 요청(예: 집계 [필터 저장] `PUT …/search-filters/…`)은 넣지 않는다** — 그 스텝은 `[예측]` 으로 보고한다.
   - `smoke.mjs`(전체 실행)는 화면·네트워크 차단이 없으므로, meta 에 변경 동작 또는 **이름으로 판정할 수 없는 클릭**이 하나라도 있으면
     `--allow-mutating` 없이는 실행하지 않는다.

## TC 불일치 처리 — continue / pass 처리 금지 (중요)
목적은 **품질 향상을 위한 테스트 스크립트**이지 '끝까지 도는 스크립트'가 아니다.
- 실제 결과가 TC 기대 결과와 다르면 **assert 는 TC 기대 그대로 둔다**. 실측 화면에 맞춰 기대값을 바꾸거나,
  `onFailure:"continue"`·assert 제거·조건 완화로 **통과시키지 않는다**. 그 assert 에서 스크립트가 실패하는 것이 정상이다.
  (`verify.mjs` 가 assert 의 `onFailure:"continue"` 를 **하드 FAIL** 처리한다.)
- 표기: `node scripts/stamp.mjs mismatch "<spec>" s20,s38 "실측: 항목 숨김"` → note `상태 불일치(TC 기대 ≠ 실측 …)`.
  ground 가 ASSERT_FAIL 로 찾은 것도 같은 표기가 된다. 보고서의 **'TC 불일치' 목록**(TC ID·TC 기대·실측)으로 사용자에게 전달.
- 구분: **대체 자원(--subst)** 때문에 다른 값/상태는 TC 불일치가 아니다 → `[예측] 대체자원 값/상태 차이`(미판정,
  `stamp.mjs data`). **명칭만 다른 경우**(버튼 `[확인]`→`[삭제]` 등 동일 기능)는 실측 명칭으로 클릭하고 note 에
  `TC [확인] — 실측 '삭제'` 로 남긴다(기능 동일 → 불일치 아님. 단 TC가 문구/명칭 자체를 검증하는 경우는 불일치).
- 실패 지점 이후 TC 를 계속 보고 싶다면 continue 가 아니라 **시나리오를 나눈다**(불일치 TC 를 별도 시나리오로).

## ground.mjs 상태값
- **FOUND**(count=1) → 실측 OK → `[실측]`.
- **MISSING**(count=0) → 셀렉터 틀림/진입점 상이/사전데이터 부재 → `[예측] 미발견`.
- **AMBIGUOUS**(count>1) → 존재하나 중복 → 순서(order/nth) 지정 필요 → `[예측] 중복`.
- **UNREACHED** → 앞 스텝(제출/누락)으로 도달 못함 → 앞 스텝 고친 뒤 재실측 → `[예측] 미도달`.
- **ASSERT_FAIL** → 요소는 있으나 상태/값이 TC 기대와 다름 → `[실측] … 상태 불일치`(TC 불일치 후보, 위 원칙대로 보고).
  `--subst` 사용 중이면 `[예측] 대체자원 값/상태 차이`(미판정).
- **POSTMUT** → 제출 결과에 의존(목록 반영·토스트 등) → `[예측] 변경 후 결과`(1회 실행으로 확인).

> 요약: **예측은 `[예측]`로 흔적 → `ground.mjs --write`로 실측 → `verify --require-grounded` PASS라야 완료.**
> "샘플 보고 지어낸" 스텝이 라이브 확인 없이 완료로 넘어가지 않도록 막는 게 이 정책의 목적이다.

## 예측 거버넌스 — TC가 SoT, 예측은 예외
- **주 목표**: 이 스킬은 **TC/기획서를 SoT(Source of Truth)** 로 삼아 명세된 동작·검증 문구를 스크립트로 만든다.
  **TC가 있으면 assert의 기대값(검증 문구·상태 등)은 TC에서 가져온다 — 예측으로 지어내지 않는다.**
  (특히 유효성 검증 '문구'를 눈대중/예측으로 넣지 말 것. 실제와 다르면 반드시 실패한다.)
- **예외(허용)**: TC가 컨텍스트로 **주어지지 않은** 경우 — 탐색적 생성·커버리지 확대(옵션 조합 검증 등) — 는 기획
  근거 없이 **현재 개발 화면을 근거로 '예측' 작성**할 수밖에 없다. **이 경우에만 예외적으로 허용**한다.
- **표기**: 예측 스텝(선택자든 기대값이든)은 note에 `[예측]`+사유. 특히 **TC 근거가 없는 예측**은
  `[예측] TC 근거 없음(개발화면 기반)` 로 명확히 구분한다.
- **보고(높은 우선순위)**: 결과 보고 시 예측 기반 스크립트를 **최상단에 별도로** 고지한다:
  > ⚠ 아래 스크립트는 **TC(기획)가 아니라 현재 개발 화면을 근거로** 작성되었습니다. **실제 Pass/Fail 판정은 사람이
  > 직접** 해야 합니다(개발 화면이 곧 정답은 아님).

## 질문지 템플릿 (TC → Tremolo 스크립트 요청 시, 작업 시작 전 1회)
이미 답을 알 수 있는 항목(워크북 첨부, 이미 등록된 계정·MFA 설정 등 — `node scripts/env.mjs` 로 확인)은 묻지 않는다.
1. **TC/기획 근거** — 워크북·시트가 주어졌으면 생략.
2. **계정** — `envs.json` 에 그 환경의 **QA 공용 테스트 계정 풀**(`account` + `accounts[]`)이 있으면 묻지 않는다.
   대상 환경에 계정이 없거나(새로 구축된 환경) 풀 계정이 모두 사용 중·로그인 불가일 때만 다음을 안내하고 **계정 ID·비밀번호 입력을 기다린다**:
   > 해당 환경에서 **중복 로그인을 금지**하고 있을 경우, **다른 사람이 사용할 일이 없는 독자적인 계정**을 사용하는 것이 좋습니다.
   > (같은 계정으로 다른 사람·Tremolo 앱·브라우저가 로그인하면 실측/실행 세션이 끊깁니다.) 사용할 계정의 아이디와 비밀번호를 알려 주세요.
   - 받은 값은 `node scripts/env.mjs set id <값> --env <키>` / `set password <값> --env <키>` 로 그 환경에 저장(이후 재질문 없음).
3. **MFA** — 다음 중 어느 것인지 묻고 결과를 안내·저장한다:
   | 응답 | 저장 | 안내 |
   |---|---|---|
   | **On + 고정 코드** | `env.mjs set mfa <코드>` | 자동화 스크립트 **작성·실행 가능**(로그인에 고정 코드 입력 스텝 포함) |
   | **On + 랜덤 코드**(요청마다 Email 등으로 OTP 발송) | `env.mjs set mfa random` | 스크립트 **작성은 가능하나 실행은 어려움** — 실측(작성) 중에는 사용자가 그때 받은 OTP 를 알려 주면 `TREMOLO_OTP=<코드>` 로 진행. **Tremolo 에서의 반복 실행은 어려움**(MFA 값이 `__OTP__` 자리표시자) — 가능하면 고정 코드 계정/MFA Off 계정을 권장 |
   | **Off** | `env.mjs set mfa off` | 로그인 동작에 **MFA 입력 스텝을 포함하지 않음** |
4. **병렬 실측(선택)** — 같은 환경용 추가 계정이 있으면 받아 `env.mjs account add <id> <pw>`, PC 가 감당할 동시 세션 수를
   `env.mjs set maxParallel <N>` 로 저장(라이브 실행이 빈 계정을 자동 배정, 연속 작업은 `TREMOLO_ACCOUNT` 로 고정).
5. **1회 실행 검증(smoke)** 여부(예/아니요). — **실측은 묻지 않고 항상 수행**한다(`qa-trml-{yymmdd}` 자원만 변경).

## 실행 검증(1회) — 요청 → 질문지 → 답변 → 생성 → 보고
스크립트 생성 요청을 받으면(형식 불문) **먼저 질문지**로 사용자 의사를 받는다. 필수 질문:
> **"스크립트 생성 완료 후, 정상 실행 가능한지 1회 실행해 검증할까요?"**
- **예** → 생성 + 정적검증 + 실측(ground) 후 **`smoke.mjs`로 '1회' 실행**하고 결과 확인. **Fail이면 분기**:
  - **TC에 있는 내용인데 Fail** → 실제 버그/개발 오류일 수 있음 → **스크립트 수정을 더 하지 말고 사용자에게 보고**.
  - **TC에 없는 내용인데 Fail** → 사용자 요청·현재 메뉴 성격·일반 통념에서 벗어나지 않으면 **수정 허용** 후 재검증.
- **아니요** → 모든 스텝 **실측 완료**만 하고 **정상 실행 여부는 미확인**으로 보고.
- 주의: 생성 시나리오의 '1회 실행'은 실제 자원을 만든다 → `smoke.mjs`는 변경 시나리오를 `--allow-mutating`
  뒤에서만 실행하고, 실행 전에 **만드는·고르는·바꾸는 자원이 모두 `qa-trml-*` 인지**(verify 경고 0)와 teardown 포함을 확인.
  (smoke 는 스펙을 그대로 돌려 `ground --mutate` 같은 화면 판정이 없다.) 읽기 전용/검증-only 시나리오는 안전.
- **환경 주의**: `smoke.mjs`(전체 스펙 실행)는 **Tremolo 리포/앱 환경 필요**(스펙이 import하는 `_helpers` + playwright config).
  **standalone**(소스 없음)에서는 라이브 게이트로 **`ground.mjs`(실측)까지만** 하고, 실제 '1회 실행'은 **Tremolo 앱에서** 수행한다.
